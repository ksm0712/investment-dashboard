# Engineering Log

Reasoning behind each phase of the performance/reliability work in `BENCHMARKS.md`. Written for an engineer who hasn't seen the code.

## Local benchmarking environment

The spec this work follows was written assuming Supabase/Postgres. This app's actual database is Turso (libSQL — a SQLite fork accessed over HTTP), confirmed by reading `lib/db.ts`: there's no Supabase client anywhere, just a hand-rolled `execute()` that POSTs to Turso's `/v2/pipeline` endpoint. That changes some mechanics (`EXPLAIN QUERY PLAN` instead of `EXPLAIN ANALYZE`, no native `(user_id, created_at)` composite the way the spec assumed, since `user_id` lives on `portfolios` not `securities`) but not the intent.

No Turso credentials existed in this checkout — only OAuth and optional market-data provider keys. Real DB-backed numbers (query plans, index effects, cache persistence) need a real libSQL backend, not the app's in-memory demo-mode fallback. `turso dev` (Turso's own local dev server) speaks the identical HTTP wire protocol as hosted Turso and needs no account, so it's used here as the benchmarking backend: installed from GitHub release binaries (Homebrew's formula required a newer Xcode than was installed, so the prebuilt `turso-cli` and `sqld` tarballs were used directly instead), running on `127.0.0.1:8080`, with `.env.local` pointed at it. `lib/db.ts` is exercised completely unmodified against it — this is not a mock, it's the same code path production runs, against a locally-hosted instance of the same database engine.

## Phase 0 — Instrumentation and baseline

**The problem**: before touching anything, find out what "the portfolio data-load path" actually is, and how slow/expensive it is today, with real numbers.

The first thing this revealed, by reading `app/api/portfolio/route.ts`, is that the spec's assumption ("the app fetches market data from the external provider on demand" on page load) doesn't hold here. `GET /api/portfolio` only reads what's already stored in Turso — `latest_price`, `target_price`, etc. — set by the last refresh. It never calls an external provider itself. The actual live-data path is `refreshPrices(userId)` in `lib/refresh.ts`, invoked from `POST /api/refresh` (manual "Refresh" button) and a daily Vercel cron. That's the function every benchmark in this project targets — benchmarking `GET /api/portfolio` instead would have produced a trivially fast, meaningless number, since it's a database read.

The second surprise: `refreshPrices` already fans out over holdings with bounded concurrency (`mapWithConcurrency(securities, 6, worker)`), not a serial loop, and each holding itself races 5+ keyless market-data providers (yahoo-finance2, raw Yahoo, Financial Modeling Prep, Nasdaq, a scrape-proxy fallback) via `Promise.allSettled`, taking whichever responds first/richest. There's no single rate-limited API to point a "the provider" story at — Phase 2 and Phase 3 are scoped around this multi-provider reality rather than the spec's implicit single-provider model.

**Instrumentation** (`lib/instrumented-fetch.ts`): an `AsyncLocalStorage`-scoped call/cache-event recorder, exposed as `timed()` (wraps one provider call) and `timedDb()` (wraps one Turso query, also capturing Turso's own server-reported `query_duration_ms`/`rows_read` — a more precise number than our wall-clock timing, since it excludes HTTP round-trip). Outside a `runWithMetrics()` scope these are no-ops (a `getStore()` check), so production route handlers pay nothing extra unless they opt in. This single module satisfies both the external-API counter (spec §0.1) and the DB-query-timing instrumentation (spec §0.3) — one generic tool, not two.

**Baseline numbers** (20 holdings, 4 currencies, 4 exchanges — `scripts/fixtures/test-portfolio.json`):
- Mean load latency: 473 ms (p50 421 ms, p95 1271 ms) for a full `refreshPrices` run.
- 100 external API calls per load (5 providers × 20 holdings — every provider is tried for every holding today).
- 0% cache hit rate — there is no cache yet.
- Slowest DB query found by ranking instrumented `execute()` calls during a full page load: the `getSecurities` join (`securities JOIN portfolios`) does a full table scan on `securities` (`SCAN s` in `EXPLAIN QUERY PLAN`, no index on `portfolio_id`) — direct evidence for the Phase 4 index, not a guess.
- Lighthouse ran against the deployed app's public route (`https://investment-dashboard-ox99.vercel.app/`) rather than an authenticated dashboard render, since Lighthouse can't carry the app's session cookie: 79/100 performance, 3.6s FCP, 3.7s LCP, 0ms TBT, 150.8 KB JS transferred.

**Tradeoff**: the 100-external-calls-per-load number is itself the strongest evidence for Phase 1 — every holding currently pays for all 5 providers because the code races them for the *richest* result (52-week range, analyst target, sector, P/E), not just the fastest price. A cache doesn't just remove redundant calls across page loads, it removes redundant calls the multi-provider race already does *within* a single load once cache-fresh data covers 52-week range/target/sector, since `marketPriceForSecurity`'s `enrich()` step only calls `marketIntelligence` when a result is missing that data.

## Phase 1 — Quote cache layer

**The problem**: Phase 0 showed 100 external calls per 20-holding load and a 473ms mean, with zero reuse across loads or across users holding the same symbol.

**Schema decision**: the spec's `quote_cache` column list (price, change_pct, high/low_52w, analyst_target, pe, forward_pe, peg, currency, exchange, fetched_at) covers what a *quote* needs, but `refreshPrices()` also writes `priceAsOn`/`marketDataSource`/`sector`/`industry`/`targetSource`/`targetAsOn` to `securities` on every refresh. A cache hit that couldn't supply those would silently null them out on the next read — a real regression, not a hypothetical one. `quote_cache` was extended with `price_date`, `source`, `sector`, `industry`, `target_source`, `target_as_on` to keep hits and misses producing identical `securities` writes. This is called out explicitly rather than silently deviating from the approved schema.

**Where caching sits**: not in front of `marketPrice()` alone — `cachedFullQuote()` wraps the *whole* price-then-intelligence sequence (`marketPrice` + conditional `marketIntelligence`) as one cached unit per resolved symbol, called from `marketPriceForSecurity`'s existing `trySymbols` loop. A cache hit therefore skips both provider races, not just the price one; a miss/stale-refresh does exactly what the code did before caching existed. This is why the external-call reduction (100%, warm) beats the price-only case.

**TTL/SWR**: implemented directly (three `env`-tunable TTLs by market phase, an in-flight `Map` for dedup, `lib/market-status.ts` for open/closed/weekend) rather than pulling in a caching library — a library would hide exactly the domain logic (TTL-by-market-hours, stale-serve-then-revalidate) this exercise is meant to demonstrate. `lib/market-status.ts` covers NYSE/NASDAQ, LSE, and NSE per the spec's minimum; an unmapped exchange defaults to the "closed" (15-minute) bucket rather than guessing "open" (60s) — the safer direction to be wrong in, and holidays aren't modeled at all (a market holiday reads as an ordinary closed evening). Both are named as gaps, not silently assumed correct.

**Serverless tradeoff**: stale-while-revalidate's background refresh is fire-and-forget from the caller's perspective, but a Vercel function isn't guaranteed to keep running detached work after its response is sent. Since this app's actual caller (`refreshPrices`) is itself one long batch operation processing many holdings concurrently, most background refreshes finish naturally before the batch does; `refreshPrices` now also calls `drainInFlightRefreshes()` (a best-effort `Promise.allSettled` over whatever's still pending) right before it returns, to maximize the odds a refresh completes before the function suspends. If one doesn't, the failure mode is just "serve stale once more next time" — not a correctness bug, since the stale value already went out correctly labeled.

**Measured effect** (same 20-holding fixture, `npm run bench`): warm-cache mean latency 473ms → 18ms (96%), external calls 100 → 0 (100%) — see `BENCHMARKS.md`. The `--cold` run (cache truncated before every iteration) intentionally reproduces the no-cache baseline; it exists as Phase 2's cold-cache comparison point, not as a Phase 1 result.

**What broke during implementation**: the first `--cold` benchmark run looked identical to baseline and briefly read as "the cache does nothing" — until re-reading `scripts/benchmark.ts`'s own `--cold` handling made clear that flag is *designed* to defeat the cache on every iteration for Phase 2, and Phase 1's real number needed a second, uncapped run. Documented directly in `BENCHMARKS.md` rather than only here, since it's the kind of result a reader could otherwise misinterpret.

## Phase 2 — Concurrency and batching

**The problem**: unlike the spec's assumption, `lib/refresh.ts` never had a serial per-holding loop — `refreshPrices` already used `mapWithConcurrency(securities, 6, worker)`. Two real gaps remained: the cap `6` was a magic number with no way to tune it without a deploy (spec §"Environment variables for all tuning knobs" is explicit about this), and every holding still made an individual FMP call even though FMP's `/stable/quote` accepts a comma-separated symbol list.

**Concurrency cap**: became `Number(process.env.REFRESH_CONCURRENCY || 5)`, one line, low risk. The spec suggests `5` as a starting point, so that's the new default. Measured honestly: dropping from `6` to `5` did *not* reduce latency in this session's runs (see the table in `BENCHMARKS.md`) — with FMP timing out on every call (see below) rather than failing fast, less parallelism cost slightly more wall-clock time. The point of this change was never "5 is faster than 6" — it's that the number is now an operational lever, not a redeploy.

**FMP batching**: `fmpBatchPrices()` prefetches all US-listed (`currency === "USD"`) auto-priced holdings' primary ticker in one (or a few, at `FMP_BATCH_SIZE` per group) `/stable/quote?symbol=A,B,C` call before the per-holding loop starts, via an `AsyncLocalStorage`-scoped map (`lib/fmp-batch.ts`) so concurrent `refreshPrices` calls — the cron already runs two in parallel — don't clobber each other's prefetch. `marketPrice()` checks this map first and, when a symbol is covered, drops "fmp" from that symbol's provider race entirely rather than calling it again.

Scoped to USD/US-listed holdings deliberately: `directPriceSymbols()`'s first candidate for a non-US holding is the bare ticker (e.g. `"HSBA"`), but FMP generally needs the exchange-suffixed form (`"HSBA.L"`) that only shows up later in that function's fallback candidate list. Prefetching the bare form for LSE/NSE/SGX holdings would likely just cache a miss under the right symbol, so those are left to the existing per-candidate resolution loop instead of forcing a batch call that's unlikely to land.

**Tradeoff not caught until it happened**: while benchmarking this phase, FMP's free-tier quota ran out mid-session (`curl` against FMP directly confirmed `{"Error Message":"Limit Reach..."}` on both single and batch requests). This made it impossible to measure the live external-call reduction from batching honestly — every run has FMP failing whether or not batching is active, so raw call counts can't isolate its effect, and `BENCHMARKS.md` marks that number **NOT MEASURED** rather than reporting a number that wouldn't mean what it claims to mean. To still verify the mechanism itself — the part that's actually new code, versus FMP's account status which isn't — `lib/fmp-batch.test.ts` tests the `AsyncLocalStorage` scoping and lookup logic directly (batch hit, miss, case-insensitivity, no cross-scope leakage between concurrent `refreshPrices` calls) without touching the network. This is the real tradeoff worth naming for this phase: a benchmark that depends on a third-party free-tier quota is itself a fragile measurement, and the mitigation was moving the *provable* part of the claim (the code does what it's supposed to) onto a test that doesn't share that fragility.

## Phase 3 — Rate limit resilience

**The problem**: nothing in `lib/refresh.ts` distinguished a rate limit (429, worth retrying after a pause) from a genuine 4xx (worth giving up on immediately), and a provider having a sustained bad day just meant every symbol kept paying for a full attempt against it on every single load, forever, with no memory of the failure.

**Design, and why it landed where it did**: the user chose "wrap each provider call uniformly" over introducing one new cached primary provider — this codebase's whole shape is "race N providers, take the richest," and singling one out as privileged would have fought that shape rather than fit it. `lib/resilient-fetch.ts`'s `withResilience(provider, fn)` is applied at exactly one place per race — the `providers` array literals in `marketPrice()`/`marketIntelligence()` — rather than inside each of the 6 wrapped provider functions individually. That's a deliberate simplification: the wrapping is identical either way, but one location is easier to audit than six, and it keeps `timed()` (Phase 0's instrumentation, already at that same call site) measuring the *whole* resilient attempt, retries included — a provider that needed 3 retries shows up as one slower call, not three separate ones, which is the right level of detail for the per-load latency numbers even though it means the "external calls" counter undercounts raw HTTP attempts during a retry storm (a real limitation, not fixed this phase).

**Structured errors**: `fetchJsonWithAttempts`/the manual `!res.ok` checks in `yahooPrice`/`yahooFallbackPrice` used to throw a bare `Error(String(status))` — nothing to branch on. They now throw `ProviderHttpError` carrying `.status` and a parsed `Retry-After` (seconds or an HTTP-date, since the spec doesn't guarantee which). `nasdaqPrice` is the one provider left throwing a plain `Error` — it internally tries two asset classes and folds both outcomes into one combined message, so there's no single status to attach; it's treated as transient (retryable) by the same rule as a network timeout, which is documented as a real, intentional imprecision rather than silently assumed away.

**Circuit breaker granularity**: the naive implementation counted every *retry attempt* toward the 5-consecutive-failures threshold, meaning a single symbol lookup retried 5 times could trip the breaker by itself before a second symbol was ever tried — clearly not "5 consecutive failures" in the sense the spec means. Fixed by only calling `recordFailure` once per `withResilience` call, after all its internal retries are exhausted — the breaker now counts failed *requests*, not failed *attempts*.

**What broke during implementation, and what it revealed**: the first `chaos-bench` run (100 iterations, cache left warm across all of them) reported a 0% failure rate for the *no-retry* baseline too — which should be impossible under 30% throttling. The cause was Phase 1's cache: after run 1 populated `quote_cache`, runs 2–100 mostly hit warm cache and never touched the mocked provider layer at all (total mock requests across 100 runs: ~170, not the low thousands a real chaos test should see). `chaos-bench.ts` now truncates `quote_cache` before every one of the 100 runs, the same way `benchmark.ts --cold` isolates Phase 2 from Phase 1. With that fixed, the no-retry baseline showed a real 3.6% security-level failure rate, and the resilience-enabled run showed 0.0% — see `BENCHMARKS.md`. This is worth naming explicitly: a benchmark that silently measures the wrong layer (cache instead of retry logic) still produces a plausible-looking, confident number, and the only way it surfaced was noticing the *absolute* request count looked too low for what 100 full runs should generate — not that the failure-rate percentage itself looked wrong.

**Tradeoff**: retries mean a failing provider now costs more wall-clock time and more real requests per symbol (`BENCHMARKS.md`: total mock requests roughly doubled, 9,156 → 19,736, for the same 100 runs) in exchange for those failures almost never reaching a security's final state. Combined with `marketPrice()`'s existing 1.8-second soft-timeout race, a symbol where every provider is failing can now hold that race open for a full retry chain (worst case, with default constants, on the order of several seconds per provider) before falling through to the second, uncapped `Promise.allSettled` wait — a portfolio with many holdings hitting a fully-down set of providers simultaneously could push a single `refreshPrices` call meaningfully closer to the Vercel function's `maxDuration`. Not a regression introduced carelessly — it's the direct cost of "retry instead of fail fast" — but a real one, and the mitigation available if it matters in practice is turning `RETRY_MAX_ATTEMPTS`/`RETRY_CEILING_MS` down via env vars for exactly this reason.

**A second, sharper thing that broke**: right after the chaos-bench numbers above were captured, a manual check in the browser (add a real MSFT holding, click Refresh) came back showing a price of exactly `$123.45` — the literal hardcoded mock price from `scripts/mock-provider-harness.ts`. The chaos-bench script and the running dev server both point at the same local `turso dev` instance (by design — that's what makes it a real database, not a mock, for everything *except* this one script). `quote_cache` is keyed globally by symbol on purpose (so two users holding AAPL share one fetch), which means `chaos-bench.ts` faking a price for `"MSFT"` and writing it through the completely real `getQuote`/`writeCache` path left that fake price sitting in the shared cache for any other consumer of that symbol to read — including the dev server serving a real user's real holding, and including any later `benchmark.ts`/`db-bench.ts` run that happened to touch the same symbols before the TTL expired. Fixed in two layers: immediately, by truncating `quote_cache` by hand against the local dev server and re-verifying with a fresh browser refresh; durably, by adding a `finally`-block cleanup to `chaos-bench.ts` itself (`DELETE FROM quote_cache` after every run, success or failure) so re-running it can never leave contaminated rows behind again. The lesson worth keeping past this one script: a mock that's faithful enough to write through the real cache/DB layer is exactly faithful enough to contaminate every other consumer of that layer, and "the mock only runs in its own script" is not the same guarantee as "the mock's *effects* stay in its own script" when the thing underneath is a shared, stateful local service rather than an in-process fake.
